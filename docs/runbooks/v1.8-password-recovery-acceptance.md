# v1.8.0 账号恢复维护与验收

## 前置条件

- 已备份生产数据库，并确认恢复演练路径。
- 配置 `UPSTASH_REDIS_REST_URL`、`UPSTASH_REDIS_REST_TOKEN`、`SMTP_HOST`、`SMTP_PORT`（465 或 587）、`SMTP_USER`、`SMTP_PASS`、可选 `SMTP_FROM`、`AUTH_RECOVERY_HMAC_SECRET`、`AUTH_RECOVERY_ENCRYPTION_KEY_ID`、32 字节 `AUTH_RECOVERY_ENCRYPTION_KEY` 和 `AUTH_EMAIL_WORKER_TOKEN`。
- 提供两个独立测试邮箱：普通用户邮箱和管理员邮箱。
- 暂停认证写入，并通知维护窗口开始。

## 迁移顺序

1. 执行 `npx prisma migrate deploy`。
2. 执行 `node scripts/migrate-admin-identities.mjs --operator <operator> --reason <reason>`；结果必须无冲突。
3. 在确认结果后执行同一命令并添加 `--apply`；生产环境额外添加 `--confirm-production`。
4. 验证 `npx prisma migrate status` 不再报告未应用迁移。
5. 迁移尚未开放前可以回滚数据库；开放认证写入后仅允许前向修复。

## Worker 调度

1. 部署到 Netlify Published deploy 后，在 Functions 页面确认 `auth-email-worker` 显示为 Scheduled；该函数在 UTC 每分钟唤醒，Preview 不应依赖自动调度。
2. 使用拥有 `worker.manage` 的超级管理员登录 `/[locale]/admin/settings`，打开“任务调度”。初始状态必须为停用；选择允许的执行间隔和批量后启用，启用前预检必须同时通过数据库、Redis、32 字节恢复密钥和 SMTP 登录。
3. 在任务调度页确认运行历史、心跳和死信；手动执行绕过间隔但不能绕过停用状态。`POST /api/internal/auth-email-jobs` 仅限 bearer token 应急调用，不能作为常规定时器。
4. 检查 `AUTH_EMAIL_DISPATCH` 任务从 `QUEUED` 到 `COMPLETED`，且 OTP 仅在 SMTP 接受后出现在 `verification`；排队超过 15 分钟必须 `DEAD_LETTER` 且不发信。
5. 对死信任务使用 `node scripts/replay-auth-email-dead-letter.mjs --job <id> --operator <operator> --reason <reason>`；生产环境添加 `--confirm-production`。

## 验收用例

1. 普通用户请求、收到 OTP、重置、旧会话失效并以新密码登录。
2. 管理员请求、收到 OTP、重置并以新密码登录。
3. 对不存在、禁用和跨范围邮箱，确认公开响应一致，审计记录失败码且不含明文邮箱。
4. 验证每邮箱/IP 限流、OTP 三次尝试、五分钟过期和重发状态推进。
5. 用超级管理员访问 `/admin/security/recovery-audit`，确认只有脱敏指纹和任务 ID。
6. 验证 SMTP、Redis 或 worker 故障不会泄漏账户状态，且审计/死信可追踪。
7. 验证 worker 连续失败或心跳超过 15 分钟未更新时 `/api/health` 返回 `degraded` 和 HTTP 200；数据库故障仍返回 `unhealthy` 和 HTTP 503。

## 不在本次验收范围

- 不部署到生产以外的目标环境后再跳过上述真实 SMTP/Redis 验收。
- 不在未完成管理员 CLI 恢复、委派恢复和邮箱变更双验证码前标记 v1.8.0 完成。
